# Cache Statusband for Codex

A small, truthful Codex port of the Claude Code Cache Keeper status band. It uses only extension points Codex actually exposes:

- Codex CLI's native status footer for live model, reasoning, context, quota, and account-supported cost data.
- A quiet `Stop` hook that saves numeric context state and a `SessionStart` hook that reports saved context, banked resets, and the session's starting account when a local session starts, resumes, or forks.
- Dependency-free `cache-statusband-codex board` and `usage` commands for local sessions and account limits.

It does **not** pretend Codex exposes a custom footer renderer, a prompt-cache warm/cold signal, or a keep-warm API.

## Requirements

- Codex CLI with plugin and hook support (tested with `codex-cli 0.169.0`).
- Node.js 20 or newer.
- PowerShell 7.2 or later for the provided installer.

## Install on Windows

From PowerShell:

```powershell
Set-Location <clone>\codex
.\install.ps1
```

The installer:

1. backs up an existing `%CODEX_HOME%\config.toml` into its own new folder under `%CODEX_HOME%\backups` (earlier backups are never overwritten);
2. registers this checkout as a local Codex marketplace (the installer asks Codex to add it; only when Codex refuses with "already added from a different source", because the checkout was moved or cloned again, the installer removes that registration, prints one line, `Re-pointing the cache-statusband-codex-local marketplace registration: <old folder> -> <new folder>`, and adds this checkout again; the plugin stays enabled. If the old folder cannot be read from `config.toml`, the line is `Re-pointing the cache-statusband-codex-local marketplace registration to <new folder>` instead. Folder paths are never compared, so a junction to the same checkout is not re-pointed (the PowerShell test covers a junction; a symbolic link or `subst` drive goes through the same code, since no paths are compared, but is not tested));
3. installs and enables the plugin and hooks;
4. configures the native Codex CLI footer; and
5. runs `npm link` in the plugin package so `cache-statusband-codex` is available in terminals.

`config.toml` and `settings.json` are each written to a temporary file beside them and swapped in with a single atomic replace (`MoveFileEx` on Windows), so a Codex or hook process opening either file never finds it missing. (If the native call cannot be compiled, the installer warns once and uses `Move-Item -Force`, which is not atomic.) A `config.toml` that contains a TOML multi-line string (written with `'''` or `"""`) cannot be edited safely: the installer stops before anything is installed or registered, says so, and leaves `config.toml` as it was; remove the multi-line string or rewrite it as a single-line string, then run the installer again. (If the string, or another value the installer cannot edit, only appears after Codex has registered the plugin, the message instead starts by saying that Codex had already registered the plugin and the install stopped part-way, and the original `config.toml` is put back as described below.) The installer needs PowerShell's FullLanguage mode: in Constrained Language Mode it stops at once with one message, having changed nothing. A `config.toml` or `settings.json` that is a symbolic link stays a link: the edit is made to the file it points at. The installer refuses a `config.toml` or `settings.json` that is a hard link, a symbolic link to a file that is a hard link, a symbolic link whose target does not exist, a circular or otherwise unfollowable chain of symbolic links, a symbolic link to a folder, or a plain folder (replacing a hard-linked file would leave the other names for it with the old content). Before Codex has registered the plugin, a refusal changes nothing and says so (`Nothing was changed.`); a refusal found only after Codex has registered the plugin leads with the sentence saying that Codex had already registered the plugin and the install stopped part-way, and the original `config.toml` is put back as described below. Validating the new `config.toml` takes a few seconds, so the installer reads it again just before the replace: if something else changed it meanwhile, it rebuilds the edit from the new text and validates again (three tries in all), and if the file keeps changing it stops and leaves it as it is. With `-SeatFile`, `settings.json` is written first, before Codex's configuration is touched, so a failure writing it changes nothing in `config.toml`. If the install fails in the registration or `config.toml` steps, `settings.json` is put back as it was (or removed, if it did not exist before) unless something else has changed it since. The hooks-review and restart notes are printed before the terminal command link step, so they always appear. A failing `npm link` (or `npm` that cannot be run or asked for its global folder) is the one later step: it does not roll anything back, because the plugin is installed and `config.toml` (and `settings.json`, when `-SeatFile` was used) are already updated; the error says so and that only the terminal command link was not made. If the install fails before that, the backed-up `config.toml` (which holds the marketplace registration and the plugin's enabled setting) is put back, though plugin files Codex already copied under `%CODEX_HOME%\plugins` are not removed, except that a `config.toml` something else has changed is left alone and the warning says where the backup is: that is the case when a re-read after Codex's registration found text the installer had not produced, and when the live file is no longer what the installer last saw. The one exception is a failure inside Codex's own registration step: its writes to `config.toml` cannot be told apart from anyone else's, so the backup is restored then regardless, and the warning says that any change made since the backup was taken is gone. (A change made in the instant between that final check and the replace cannot be detected.)

Codex runs the plugin's hooks from its own installed copy of the plugin (under `%CODEX_HOME%\plugins\cache`), not from your clone. After pulling updates, re-run `install.ps1` so Codex installs the new version. A relative `-CodexHome` resolves against the current PowerShell location, as a relative `-SeatFile` does.

Codex also marks a plugin's hooks **untrusted** until you review them, and untrusted hooks do not run. After installing, open `/hooks` in the Codex CLI to review and trust the two hooks this plugin adds (`SessionStart` and `Stop`); in the desktop app, review the hooks when Codex prompts. Codex remembers a hash of each reviewed hook, so the review repeats after an update that changes them.

On Windows the readers launch `codex.exe` found on `PATH`, or npm's `codex.cmd` through `cmd.exe`; set `CODEX_BIN` to choose a specific launcher. A `.cmd` or `.bat` path containing `%` is refused because `cmd.exe` cannot escape it: point `CODEX_BIN` at `codex.exe` or move the install. Such a wrapper is skipped when a usable `codex.exe` or `codex.cmd` appears later on `PATH`, and when none does, `usage` and `board` print the refusal on stderr.

Restart Codex after installation. In the CLI, `/statusline` can reorder or remove footer items. Use `-KeepExistingFooter` to preserve an existing footer, or `-SkipCliLink` to install only the Codex plugin:

```powershell
.\install.ps1 -KeepExistingFooter
.\install.ps1 -SkipCliLink
```

For an account rotator, optionally point the installer at the file containing the current seat label:

```powershell
.\install.ps1 -SeatFile (Join-Path $HOME ".codex\.active-account")
```

The setting is stored as `%CODEX_HOME%\cache-statusband-codex\settings.json`. When the file contains a nonempty label, companion output ends with `Seat <label>`. A missing `settings.json`, or one with no `seatFile` key, means no seat. (The trade-off: a missing `settings.json` means "no seat" at once, unless the installer's temporary file is beside it, so an editor that deletes the file and recreates it can briefly be read as "no seat", and a session starting in that instant would show the account email.) A `seatFile` that is not a non-empty string, an unreadable `settings.json` or invalid JSON makes the seat unavailable, as does a configured seat file that is missing or empty. With an unavailable seat, a new session or a CLI run shows nothing: no label, no email and no usage reading, until the file holds a label. A resumed session shows the reading for its starting account (cached, or read live if the login still matches) instead, with its recorded `Seat <label>` if it has one and never its email (with any seat configured, available or not, the email it recorded is not shown). A resumed session words this as history, `Started as <label>.` and `Banked resets (starting account): N`, because the login in use now may not be the one it started under; new and forked sessions say `Account: <label>.` and `Banked resets: N`. (A read or parse failure of `settings.json` is retried briefly first, and so is a missing file, twice (about 100 ms in all), but only while the installer's temporary `.settings.json.*.tmp` file sits beside it, which means a replacement is under way; a missing `settings.json` with no such file means no seat at once. So a `settings.json` being replaced at that moment is not mistaken for a broken one or for no seat.) (The seat file itself is read the same way: a read that fails or finds it empty is tried again up to three times, 50 ms apart, before the seat counts as unavailable, so a seat file caught while it is being rewritten is not taken for a missing seat.) Sessions started before any identity was recorded never show usage on resume: a resumed session is not re-captured, because today's login cannot establish the one it started under. Without any seat setting, output ends with the email returned by Codex. `CACHE_STATUSBAND_CODEX_SEAT_FILE` can override the saved path for one process. No seat is inferred when neither setting exists.

The installer and runtime never read `auth.json` or any token. The installer does copy `config.toml`: to a temporary file for validation (removed afterwards) and to a backup folder under `%CODEX_HOME%\backups` on every run, which is never pruned. Those backups hold whatever `config.toml` holds, including any secrets placed in it.

## Codex CLI footer

The default preset is:

```toml
[tui]
status_line = ["model-with-reasoning", "context-remaining", "five-hour-limit", "weekly-limit", "estimated-thread-cost", "current-dir", "git-branch"]
status_line_use_colors = true
```

These are Codex-native components, not custom-rendered segments. `estimated-thread-cost` appears only when the signed-in workspace supplies an estimate; the port never guesses a price. Five-hour and weekly windows likewise appear only when Codex supplies them. Codex has no built-in banked-reset footer item, so that count appears in the companion command and resume hook instead.

## Session board

```powershell
cache-statusband-codex board
cache-statusband-codex board --all --limit 100
cache-statusband-codex board --json
cache-statusband-codex usage
cache-statusband-codex session "$env:CODEX_HOME\sessions\YYYY\MM\DD\rollout-....jsonl"
```

`usage` captures the configured seat or signed-in email with `account/read` (with a seat configured, the signed-in login is read a second time, on the same app-server connection, after the seat file is last checked, and the capture fails if no one is signed in, if the login has no ChatGPT account email, or if the login changed), then reads five-hour/weekly limits and `rateLimitResetCredits.availableCount` through Codex app-server ([official account protocol](https://learn.chatgpt.com/docs/app-server#1-check-auth-state), [official rate-limit protocol](https://learn.chatgpt.com/docs/app-server#8-earned-rate-limit-resets-chatgpt)). `refreshToken` is false. `board` prints the same usage header, ending with that captured email or seat, then scans active rollout JSONL files under `%CODEX_HOME%\sessions`; `--all` also includes `%CODEX_HOME%\archived_sessions`. It extracts only session metadata and the latest token-count record; prompt and response fields are never inspected, printed, or retained. It does not depend on Codex's private SQLite schema.

Human-readable `usage` output lists up to 20 reset details Codex returns, with an absolute date/time in the machine's local timezone and a relative countdown; a reset whose `expiresAt` Codex sent as an explicit `null` reads "does not expire", while one with no usable `expiresAt` reads "expiration not supplied". Only reset rows Codex marks `available` (or sends with no status) are listed: rows with another status (Codex's `redeeming`, `redeemed` or `unknown`) are dropped and counted apart as `creditsNotAvailable` (a number carried in the stored reading and in `usage --json`), and whenever any were dropped they are named ("N reset rows with another status not shown"), even if no usable row is left. Codex's count may or may not include such rows, so when any were dropped a remaining gap is worded neutrally ("M more reset expirations not listed") and is not reduced by them; "not supplied by Codex" is said only when no row was dropped for its status. `usage --json` retains the raw Unix-seconds `expiresAt` value. When a seat is configured, `usage --json` and `board --json` omit `accountEmail` and `identityKey`, since the seat label is then the displayed identity. If reading usage fails outright, `board` still lists the sessions: it prints `cache-statusband-codex: usage not read: <reason>` on stderr, shows the usage header as unavailable, and `board --json` carries `"usage": null` next to the sessions, so check for null before reading its fields. When the login itself cannot be read, `usage` and `board` print one line on stderr saying why (for example `cache-statusband-codex: usage not read: Codex was not found ...`, `... Codex could not be started (<code>)` (a spawn-time failure such as `EACCES`, `EPERM` or `EINVAL`), `... Codex exited before answering` (a broken pipe or reset connection while the account was being read), `... Codex account read timed out`, `... Codex app-server exited before the account response (<code>)`, `... Codex account read failed`, `... The seat changed during the account read` and `... The Codex account changed while the seat was being confirmed` (a seat or login that changed while it was being read; if the seat is configured but unreadable by then, the line is left out as for any unavailable seat), `... no Codex account is signed in` (only when Codex reports no login at all), or `... the signed-in Codex login (<type>) has no ChatGPT account email, so usage cannot be read` (an API-key, Amazon Bedrock or similar login, or an email that fails validation; `<type>` is Codex's login type, or `unknown type`), show usage as unavailable on stdout and still exit 0. A configured seat label that cannot be read stays silent: that is a deliberate fail-closed state. The compact board header and resume hook show only the nearest countdown. If Codex returns an authoritative count without detail rows, the command says that expiration details were not supplied instead of inventing dates. At most 20 detail rows are kept; if Codex sent more, the command says how many more are not shown, which is different from rows Codex did not supply. Rows Codex sent beyond its own count are described against that count ("N more rows beyond Codex's count of X not shown").

Usage reads are shared under `%CODEX_HOME%\cache-statusband-codex` separately for each verified account email: at most one rate-limit attempt every five minutes per account, even when two seat labels refer to it. A server `Retry-After` extends that delay up to one hour. Failed checks retain the complete last-good reading and change only attempt/error timing. Each usage read asks Codex for the signed-in account first and sends `account/rateLimits/read` only if that email matches the captured one (compared without regard to case). If the login differs or no one is signed in, no rate-limit request is made at all: the login is checked immediately before the rate-limit request is sent; the check is recorded as a failed one and nothing is stored for the other account. A seat label never authorizes another account's readings. Upgrading a seat-keyed cache preserves its polling deadline while discarding its unverified values. Cache filenames contain only one-way identity hashes. The cache holds only: its format `version` number, the sanitized email and the identity key built from it, the aggregate reset count, each listed reset's display title and expiry (with a flag when Codex said a reset does not expire), the number of reset rows cut by the 20-row cap and the number dropped for their status, each limit window's percentage used, length in minutes and reset time, and the attempt, fetch and error timestamps. When the shared attempt marker cannot be written, the cache folder cannot be created, or the lock file cannot be created and a small probe file cannot be created beside it either (the folder refuses new files, the disk is full, or the folder is read-only or missing: a cache that cannot be written at all), no live read is made, so the five-minute limit holds; the stored reading, if any, is shown as stale. (A lock file that is refused for a moment, as when a scanner has it open, is tried again a few times and then counted as another process reading usage: the stored reading is shown without the message below. For `EPERM` and `EACCES` that holds as long as the folder still accepts new files; `EBUSY` means another process has the lock file open, so it always counts as busy.) `usage` and `board` say why, `Usage not read: cannot update the cache in <cache folder>` (the CLI also prints it once on stderr; `--json` carries `cacheUnwritable` and `cacheDir`); the SessionStart hook shows only the stored reading and does not give the reason. Account IDs, reset IDs, descriptions, raw responses, and credentials are discarded. The port never calls `account/rateLimitResetCredit/consume`; it can display a banked reset but cannot spend one.

`SessionStart` stores its initial account key and display label once per session ID using `getSessionIdentity` in `src/session-state.mjs`. Resuming that ID reuses the saved identity, even after a shared seat file or login changes. Simultaneous starts publish one complete record without overwriting an existing one. If the record cannot be saved, for any reason (the folder refuses new files, the disk is full, the file system has no hard links), the save is tried again twice when the refusal may be momentary, and a record that another start published meanwhile is used if there is one; otherwise that start still shows the login it just read, unrecorded, and a later resume of the session finds no record, treats it as unknown, and shows no usage. (A record that is there but cannot be read or parsed is different: that start shows nothing, the session is unknown, and a later resume finds the same corrupt record and treats it as unknown too.) If the start-time capture is unavailable (a timeout, no signed-in account, or the login or seat changing mid-read), the session remains unknown and never shows usage, because a resumed session is not captured again; a corrupt or unreadable record is not replaced with a later account. Sessions resumed from an older plugin version without an identity record also remain unknown: the original login cannot be reconstructed from today's account. Standalone `usage` and `board` commands capture the current identity for each invocation. No cache-warm/cold state is inferred from any account change.

Companion segments capitalize their first word, matching the current original. Email casing and digit-led labels such as `5h` are preserved. Codex owns capitalization in its native footer.

This is an external command, not `/board`: Codex does not expose third-party slash-command registration.

The board selects candidates by filesystem modification time and applies `--limit` before parsing transcript bodies, continuing to the next candidate if a file moved during the scan. Directory discovery and file metadata are still scanned, but old transcript bodies beyond the limit are not read.

## Codex desktop app

The plugin and `SessionStart` hook also load in the local Codex desktop app. On a session with a saved token report, the hook shows a short message such as:

```text
Cache Statusband Codex: restored current-model/high; saved context 83.4k/258k (32%); last token report 4m ago. Prompt-cache warm/cold state is not exposed by Codex. Banked resets (starting account): 2; next expires in 1d4h Started as <label>.
```

The desktop app does not expose a custom persistent footer slot, so the CLI status line is not injected into the app. The board can still be run in a terminal, including a terminal panel opened from Codex.

| Original feature | Codex port |
|---|---|
| Coloured model and effort band | Native CLI `model-with-reasoning` footer item with theme colours; no custom powerline renderer |
| Context used/window | Native live footer plus saved context in the resume hook and board |
| Five-hour and weekly usage/reset | Native live footer items plus the cached `usage`/`board` read |
| Banked earned resets | `usage`, the board header, and the CLI/desktop resume hook; read-only, never redeemed |
| Signed-in account | Sanitized `account/read` email in `usage`, board, and the CLI/desktop resume hook; an explicitly configured seat file overrides it |
| Session cost | Native `estimated-thread-cost` only when the workspace supplies it; never synthesized |
| Reopened-session measurement before first send | `Stop` saves a small numeric snapshot after replies; `SessionStart` prefers the bounded transcript read and falls back to that snapshot |
| `/board` of local sessions | `cache-statusband-codex board`; external because custom slash commands are unavailable |
| Seat label for account rotators (`seatFileTerminal`, `seatFileDesktop`) | `install.ps1 -SeatFile` or `CACHE_STATUSBAND_CODEX_SEAT_FILE`. One file serves the CLI and the desktop app (the original has one per surface), is read when a session starts and is bound to the verified account; `rotatorWakePattern` has no counterpart: the original's rotator wake-up prompt marks the cache cold and takes up the new account's seat mid-session, but the port reads the seat file only when a session starts and cannot take it up mid-session, and it tracks no cache state to mark cold |
| Usage on a fresh or reopened chat | One shared, per-account usage reading (at most one rate-limit request every five minutes) used by `usage`, `board` and the resume hook. The original also borrows the freshest open chat's figures; the port has no such source, and the native footer carries Codex's own live numbers |

## What did not port, and why

| Feature | Why it was not ported | Closest truthful Codex behavior |
|---|---|---|
| Prompt-cache warm/cold state | Codex reports what a completed request read or wrote, but exposes no supported signal proving whether the **next** request will hit the same cache | Show prior cached-token accounting only; label next-request state unknown |
| Cache rewrite countdown / Claude's 5-minute-or-1-hour state | Codex does not expose a user-selected cache TTL or a per-session expiry timestamp. OpenAI caching is automatic, and a documented minimum lifetime is not a guaranteed eviction time | No countdown is shown |
| Keep-warm pings | Hooks have neither a background timer nor a supported “refresh this cache” call. A synthetic turn would consume quota and still would not guarantee routing to the same cache | Send nothing; let Codex manage caching automatically |
| Auto-resume after usage renews | A shared-daemon CLI watcher can receive typed `UsageLimitExceeded`, read the real reset time, and later invoke `codex queue`. However, checking the latest turn and queuing `Resume` are separate server operations: `turn/start` and the thread queue APIs expose no expected-turn precondition, so a user message can win the gap without reliably canceling the automatic spend. The desktop app also keeps its app-server on private stdio | No setting or watcher is installed. Codex needs an atomic “start only if this failed turn is still current” operation before the original cancellation rule can be guaranteed |
| Cold-chat guard: compact a big cold chat, then send the message (`/cache guard`, `/cache big`) | The original needs two things the Codex surface does not give this port. First, a cold/warm verdict (see the first row: Codex exposes no signal for whether the next request will hit the cache). Second, holding a prompt on its way out, compacting the live chat and sending the prompt after it, including the continue Claude Code sends after a usage limit resets. Codex 0.169's protocol schema lists a `userPromptSubmit` hook and a `thread/compact/start` request, but this port has not verified that a hook can hold a prompt, start a compaction on the running thread and send the prompt afterwards. Estimating a rewrite charge instead would be false precision and could delay a perfectly valid send | Nothing is compacted or held. The resume message reports saved context age and explicitly says cache state is unknown |
| `/cache` status and settings (`ttl`, `guard`, `big`, `alerts`, `autowarm`) | Every one of these tunes cache behaviour that does not exist here (a cache lifetime, the cold-chat guard, cool-down alerts, automatic keep warm), and Codex has no third-party slash commands to carry them | The port's own settings are `install.ps1` flags (`-SeatFile`, `-KeepExistingFooter`, `-SkipCliLink`) and the `CACHE_STATUSBAND_CODEX_SEAT_FILE` variable |
| `/keepwarm [hours\|off]`, automatic keep warm and the `prPattern` stop | Same reason as the keep-warm pings row: there is nothing to keep warm, and a hook cannot run on a timer | None |
| Cool-down and "waiting on you" alerts (`/cache alerts`) | The cool-down alert counts down to a cache expiry that Codex does not expose, and this port's hooks run only when a session starts or a reply finishes, so they have no timer to raise an alert from | None |
| Rewrite cost estimate (`Rewrite ≈ $`) and cold-rewrite tally (`Cold rewrites $ (n)`) | Both price a cache rewrite, which needs the cold/warm state and a per-token price table; neither exists for Codex, and guessing a price from public model prices would misstate subscription usage | None; native `estimated-thread-cost` appears only when the workspace supplies it |
| `/handoff [continue]` and the Cache Keeper handoff button | A slash command, a clickable button on the band, and driving `/clear` followed by sending the handoff as the new chat's first prompt are all mod abilities Codex does not offer a plugin | None; ask the agent for a handoff in the session by hand |
| The `session-handoff` skill | Not included in this port. This is a gap, not a Codex limit: the 0.169 plugin schema lists skills a plugin can carry. The skill's text is written for Claude Code (it reads `~/.claude/plans`, Claude memory files and `run_in_background` shells), so it needs a Codex rewrite that was not done here | None |
| Arbitrary colour blocks and powerline arrows | `tui.status_line` accepts built-in component IDs; it cannot run an external command, interpolate a template, or accept arbitrary ANSI segments | Native theme-coloured footer components |
| Banked resets as a persistent footer segment | `account/rateLimits/read` exposes the data, but `/statusline` has no banked-reset component and Codex has no custom footer slot | Show the count in `usage`, `board`, and the resume hook |
| Account email as a persistent footer segment | `account/read` exposes the email, but `/statusline` has no account/workspace/custom-text item | Show the email or configured seat in companion output and the resume hook |
| Recording-aware account masking | Codex exposes no plugin-visible recording-mode flag equivalent to the original's local recording state | No automatic masking is claimed; use a seat label when the email should not be displayed |
| General dollar-cost calculation | ChatGPT subscription quota is not API billing, and Codex supplies no universal per-thread dollar total. Guessing from public model prices would misstate subscription usage | Native `estimated-thread-cost` only when the workspace supplies it |
| Claude/Fable-specific weekly usage | Fable is an Anthropic model/bucket and has no Codex equivalent | Codex's own five-hour, weekly, and named account buckets when supplied |
| `/board` as a slash command | Codex does not expose third-party slash-command registration | External `cache-statusband-codex board` command |
| Persistent band inside the desktop app | The desktop app supports hooks but does not expose the CLI TUI footer or a plugin footer slot | Resume `systemMessage`; board/usage in a terminal panel |

OpenAI prompt caching is automatic. Current OpenAI API documentation describes minimum cache lifetimes and cache-write/read pricing, but Codex does not expose a user-controlled cache policy or reliable warm/cold state through its supported configuration and hook surface. See [OpenAI prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching).

## Privacy and network behavior

- A read-only `account/read` (`refreshToken: false`) captures identity at command/hook start; `account/rateLimits/read` is shared per identity, sent only after `account/read` confirms the expected account, and attempted at most once per five minutes.
- A longer structured or textual `Retry-After` delays the next attempt up to one hour; failures retain the last good data and never become a fake zero. One parser reads both the error's structured data (`retry_after`, `retryAfterSeconds`, `retry-after-ms`, `retry_at` and similar, in any case, with a unit in the key name) and its message text. A message has two kinds of key: a header form (`Retry-After`, `retry_after` or `retry-after`, with or without a unit in the key name, followed by `:` or `=`) and a prose form (`retry after` or `retry at` followed by a space). Only what comes immediately after the key is read (allowing only spaces, `:`, `=`, a spaced dash, `in`, a quote or `(`, and the filler `about`, `approximately`, `around`, `at least` or `~`), and only as a duration (counts with units from milliseconds to weeks; compounds such as `1h30m` or `1 hour 30 minutes` are summed, and a list of durations joined by `or`, `to`, `-`, an en or em dash, a comma or whitespace, such as `30 minutes or 2 hours`, `5m-3h` or `1m 2h`, is read as its longest), a moment (ISO dates, a date-time with no zone being UTC, a date with no time being the end of that day in UTC, and HTTP-dates) or a bare whole number (seconds), the last only when followed by the end of the text, a newline, whitespace and then the end, or one of `. , ; ) ] }` (never before `(`, a quote or a digit). Text after a complete wait (an id, a year, `your 5 hour usage is high`) is not read, and a unit glued to more letters or digits (`7d9f3`) is not a unit. A value that is not in that form is unparsed. After a prose key that means there is no key at all (`retry after reconnecting`, `retry at most 3 times`, `retry at any time`, `retry after 10 (about 10 minutes)`); after a header key it means the server named a `Retry-After` it did not make readable, and that is read as the one-hour cap (`Retry-After: soon`). `null` or `none` after either key is no key. A wait that parsed, in the structured data or in the text, always wins over a cap, which answers only when nothing parsed at all; a structured value that is an object is read as `{secs, nanos}`, `{seconds}` or `{ms}`, and any other non-null object, an array or a boolean is the cap. No `Retry-After` at all leaves the normal five-minute floor.
- No direct usage HTTP request and no reset-consumption call.
- A usage read starts a short-lived Codex app-server in your `CODEX_HOME`. A `SessionStart` makes at most two such starts: one for the identity capture (with a seat configured, both account reads share it) and one for the usage read, which is skipped while the shared five-minute reading is fresh; a resumed session makes no capture, so at most one. `usage` and `board` make the same two. Codex does its own startup work there (for example its curated-plugin sync) and may leave temporary folders under `%CODEX_HOME%\.tmp`, as Codex itself does when stopped early. In our tests, an app-server stopped early left a partial clone of Codex's curated plugins of several megabytes under `%CODEX_HOME%\.tmp`.
- No reads of authentication files, environment tokens, or private SQLite tables.
- The cache stores the sanitized email but no account ID, reset ID, description, credential, token, or raw app-server response.
- Rollout parsing is bounded to a 256 KiB head and 2 MiB tail and never extracts, emits, or stores message content. On a file larger than both, the model and effort come from the latest turn record that names a model found in the tail or, failing that, in about 1 MiB just before it; if none is found there, and that stretch does not reach back to the head window, they are shown as unknown rather than taken from the first turn. (When that stretch does reach the head window, which holds for files up to about 3.25 MiB, the head's turn context is the latest there is and is used.) The working folder follows the same rule: a turn record's folder is used only together with its model and effort, and a turn record that names no valid model is ignored altogether (its effort and its folder included), so an unknown model is never paired with an earlier turn's folder (the session's starting folder, from its first record, is kept). A turn context is taken as a whole for the model and effort: one that names a model and no effort leaves the effort unknown, never an earlier turn's. The look-back reaches 64 KiB below the head's end so a turn record that crosses the head's cut-off is still seen.
- After a reply, `Stop` atomically saves only context tokens/window, model, effort, and report time in a small per-session file. `SessionStart` uses it when a rollout cannot provide an equally recent report. One rule keeps the model, in `Stop` and on resume: a report that names neither model nor effort keeps the pair saved before, while one that names a model replaces both (a new model is never paired with an old effort; a turn record that names no model is ignored, so a rollout never reports an effort alone). The kept pair is the one saved after the earlier reply, so if the model was switched during a single very long turn, the pair kept (or shown on resume) can be an earlier turn's until a report names the new one. On resume, a transcript that names neither, with the very same token-report time as the saved snapshot, shows the saved pair instead of "unknown model".
- Hook errors fail open with an empty response; they never block a Codex session.

Codex documents transcript JSONL as convenient but unstable. The parser is defensive, and an unknown future record shape produces missing fields rather than invented numbers.
